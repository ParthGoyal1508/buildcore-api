## 1 — The up-to-previous column, and the footer identity that cannot fail

The risk: FR-035 is the one property of a package that cannot be checked by reading a single bill,
and it is also the property most easily made true by construction. A test that cannot fail is worse
than no test, because it is counted as cover.

- [ ] CHK001 Is the up-to-previous figure defined **once**? FR-014 requires it be "read from the
      previous bill's stored up-to-date position" and "MUST NOT be recomputed from current data";
      data-model.md states it is "**not stored** … this bill's up-to-date minus this bill's own
      amount". Those are two different figures whenever the chain has a gap, a revision or a
      correction. [Conflict, Spec §FR-014, Data-model §BillPackage]
- [ ] CHK002 **Does FR-035 state an identity that can be violated?** If up-to-previous is derived
      as up-to-date minus this bill, then `thisBill + uptoPrevious = uptoDate` is an algebraic
      rearrangement of its own definition and holds for any values whatever. The plan calls this
      test "the one property of the package nobody can check by reading a single bill"; as written
      it is satisfied by construction. [Conflict, Spec §FR-035, §SC-004, Plan §Test strategy]
- [ ] CHK003 Is "the previous bill" defined — previous by sequence number, by period, or by issue
      date? Those three orderings can disagree, and nothing states which governs.
      [Ambiguity, Spec §FR-014]
- [ ] CHK004 Does any requirement state the up-to-previous position of the **first** bill? Zero and
      absent are different things on a document whose reader subtracts columns.
      [Gap, Spec §FR-013, §FR-014]
- [ ] CHK005 Is it stated whether the chain reads the previous **issued** bill or the previous bill
      in sequence? FR-014a freezes the cumulative position at issue, so a draft sitting between
      two issued bills has no stored position to read — and nothing says whether it is skipped or
      is an error. [Gap, Spec §FR-014, §FR-014a]
- [ ] CHK006 Is the abstract of a **draft** bill specified? The contract exposes the abstract before
      issue, FR-014a stores the cumulative position only at issue, and no requirement says what the
      up-to-date column shows in between. A figure that changes when the engineer presses Issue is
      a figure they did not approve. [Gap, Spec §FR-014a, Contract §GET abstract]
- [ ] CHK007 Does any requirement extend FR-035's identity to the abstract's **money**? FR-035
      binds the measurement sheet's quantity footer only; the three money columns are required to
      "balance independently" (FR-021), which is a weaker and different property.
      [Gap, Spec §FR-021, §FR-035]

## 2 — The subcontractor direction, and where its quantities come from

The risk: this is the direction the company actually bills every month, and the measurement feature
does not measure the schedule it bills against. A proposal of zero is indistinguishable from a
month in which nothing was done.

- [ ] CHK008 **Does FR-003 name the right schedule?** It requires a proposal for "every BOQ line in
      the project". A bill to a subcontractor measures `WorkOrderBOQItem` — that subcontractor's
      award lines — not the project's BOQ, which research §1 and plan Phase A both state. Read
      literally, FR-003 puts 312 project lines on a 17-line subcontract bill.
      [Conflict, Spec §FR-003, Research §1, Plan §Phase A]
- [ ] CHK009 Is the measurement source for an award line stated anywhere? Feature 022 attributes
      measurement to `DWRTask.boqItemId` — a **BOQ** line. `WorkOrderBOQItem.boqTaskItemId` is
      **nullable** by design ("a subcontract can cover work the client's BOQ itemises
      differently"), so an award line with no link has no measurement to be proposed from.
      [Gap, Spec §FR-003, Schema §WorkOrderBOQItem]
- [ ] CHK010 **What is proposed for an award line that maps to no BOQ line?** Zero is the obvious
      implementation and is indistinguishable from "nothing was done this month" — on the direction
      the user named as their primary case. Nothing requires the two be distinguishable.
      [Gap, Spec §FR-003, §FR-030]
- [ ] CHK011 Is the many-to-one case specified? Two award lines pointing at one BOQ line would each
      be proposed that line's full approved measurement — the same quantity claimed twice on one
      bill, with FR-008's one-line-per-item rule satisfied because they are two different items.
      [Gap, Spec §FR-003, §FR-008]
- [ ] CHK012 Does FR-012's work-done figure match the line amounts it is meant to total?
      `ClientBillLine.amount` is `quantity × rate × (1 + quotedPercentage)`; FR-012 defines work
      done as "the sum of each line's claimed quantity at its frozen rate", which omits the quoted
      percentage. The Annexure footer and the abstract would then disagree whenever a tender was
      quoted above or below the schedule. [Conflict, Spec §FR-012, Schema §ClientBillLine]

## 3 — The real document's zeros

The risk: SC-003 reproduces one real bill, and that bill's withheld amount and several of its
recoveries are zero. A test built from it passes while every path the real bill did not exercise is
wrong.

- [ ] CHK013 Is SC-003 reproducible from the figures it states? Work done 18,41,686 with tax
      1,65,752 + 1,65,752, retention 92,084 and tax deducted 36,834 gives a total of 21,73,190 less
      1,28,918 — which is 20,44,272, not the stated payable of 11,39,971. The remaining 9,04,301 of
      recoveries and deductions is **not stated**, so the criterion can only be met by inventing
      figures that make it true. [Measurability, Spec §SC-003]
- [ ] CHK014 Is the rounding rule stated? 9 % of 18,41,686 is 1,65,751.74 and the document shows
      1,65,752; 2 % is 36,833.72 against a shown 36,834. Money is `Decimal(18,2)`, so neither
      figure is reachable without a rounding rule, and no requirement names one.
      [Gap, Spec §FR-015, §FR-019, §SC-003]
- [ ] CHK015 If each row is rounded, does FR-021's "each column balances independently" still hold?
      Rounding rows and then summing, versus summing and then rounding, differ by rupees — and
      FR-021 is the requirement that would catch it only if it states which is intended.
      [Clarity, Spec §FR-021]
- [ ] CHK016 **What base does tax apply to?** FR-015 says "tax on the work done". Block A of the
      real abstract carries a *release withheld* amount beside the work done, and nothing states
      whether the withheld amount adds to or subtracts from the taxable base, or whether it is
      taxed at all. It is zero on the sample bill, so SC-003 constrains none of this.
      [Gap, Spec §FR-015, §SC-003]
- [ ] CHK017 Is retention's base stated? 5 % of the gross work done reproduces 92,084; 5 % of the
      post-withholding or tax-inclusive figure would not. FR-018 names where the *percentage* comes
      from and is silent on what it multiplies. [Gap, Spec §FR-018]
- [ ] CHK018 Is the tax-deducted base stated? Same shape as CHK017: FR-019 fixes the rate's source
      and not the base, and 2 % of the gross rather than of the post-recovery payable is what the
      real document does. [Gap, Spec §FR-019]
- [ ] CHK019 Is the tax basis fallback a **reportable** condition or a silent default? `Client`
      carries no `state`, so for a bill to a client FR-016's derivation depends entirely on reading
      the state out of the registration number — and where that is absent too, `from_project_flag`
      is recorded on the row. Nothing requires anybody be told.
      [Gap, Spec §FR-016, Research §5]

## 4 — The one-time deduction that is "fully recovered"

The risk: a requirement satisfied by doing nothing. This is the shape 022's FR-040 had before it was
rewritten.

- [ ] CHK020 How is "fully recovered" determined? FR-020 requires a fully-recovered one-time
      deduction to appear in the cumulative columns and be absent from this bill's — but no table
      records what the deduction's **total** is, so nothing distinguishes "fully recovered" from
      "entered as zero this month". [Gap, Spec §FR-020, Data-model §BillPackage]
- [ ] CHK021 **Is FR-020 satisfiable by inaction?** If the per-bill amount is whatever was entered
      and the cumulative is the sum of what was entered, then an implementation that does nothing at
      all satisfies FR-020 for every bill. A requirement no implementation can fail is not a
      requirement. [Conflict, Spec §FR-020]
- [ ] CHK022 Is the mobilisation advance's balance stored anywhere? Recovering an advance over
      several bills requires knowing what remains, which is the same missing figure as CHK020 and
      has the same consequence — money recovered twice, or never.
      [Gap, Spec §FR-017, Data-model §BillPackage]
- [ ] CHK023 Does any requirement forbid the cumulative column of a one-time deduction exceeding its
      total? The real package's performance security is 3 % of the work-order amount "as per Clause
      13", which is a figure the system could check against and does not hold.
      [Gap, Spec §FR-020, §FR-023]

## 5 — The live register inside a frozen bill

The risk: FR-028 and FR-039 are both reasonable and they cannot both be obeyed.

- [ ] CHK024 Is a debit applicable to an **issued** bill? FR-037 and FR-038 require an applied debit
      to be included in that bill's recoveries; FR-044 freezes the bill's figures at issue. Nothing
      states that application is a draft-only operation, and applying one afterwards either moves a
      frozen figure or records a recovery the bill never made.
      [Gap, Spec §FR-037, §FR-038, §FR-044]
- [ ] CHK025 **Do FR-028 and FR-039 conflict?** FR-039 requires any bill's register to show every
      debit recorded against the project — quickstart Pass 6 expects a *later* package's debit to
      appear — while FR-028 requires every figure in the workbook to come from the stored bill and a
      bill produced twice to be identical. A debit recorded between two productions of one issued
      bill satisfies one requirement by violating the other.
      [Conflict, Spec §FR-028, §FR-039, §SC-009, Quickstart §Pass 6]
- [ ] CHK026 Is "byte-for-byte identical" satisfiable? FR-028 says the workbook must be
      byte-for-byte identical in its figures; an `.xlsx` is a zip carrying creation and modification
      timestamps, so no two productions are ever byte-identical. SC-009's "identical in every
      figure" is the satisfiable statement and FR-028 should say that and nothing more.
      [Clarity, Spec §FR-028, §SC-009]
- [ ] CHK027 Which of the four named recovery kinds does an applied debit land in? FR-038 says "that
      bill's recoveries" and FR-017 names four; nothing maps a debit to one of them, so two
      implementations could both be compliant and disagree on the abstract.
      [Ambiguity, Spec §FR-017, §FR-038]
- [ ] CHK028 **Is the one-bill rule enforced against two simultaneous applications?** FR-037 refuses
      "a second application", which reads as sequential. data-model.md settles on a conditional
      update whose row count the service checks — a design, not a requirement. 022 had to promote
      exactly this property from an edge case to FR-014a before it was testable.
      [Gap, Spec §FR-037, Data-model §BillPackageDebit]

## 6 — The period that is billed once

The risk: FR-049 retires the provenance link on the strength of "a period is billed once". If that
sentence is not true, the measurement behind a claim becomes unknowable — and it is not true as
FR-002 is written.

- [ ] CHK029 Is FR-002's overlap check scoped correctly? It refuses "a period that overlaps a period
      already billed **on the same project**" — but one project is legitimately billed to its client
      and to several subcontractors over the same month. Read as written, the second subcontractor's
      bill is refused. [Conflict, Spec §FR-002, §FR-025]
- [ ] CHK030 Given CHK029, does FR-049's construction argument still hold? "A period is billed once"
      must become "one line of one schedule is billed once in one period" for the claim to be true
      per counterparty, and FR-049 cites FR-002 and FR-007 as its proof.
      [Conflict, Spec §FR-049]
- [ ] CHK031 Does "already billed" mean a package that exists, or one that has been issued? Two
      drafts over overlapping periods would both propose the same approved measurement, and nothing
      states which statuses occupy a period. [Ambiguity, Spec §FR-002]
- [ ] CHK032 Is there a way to abandon a draft? `BillPackageStatus` is `draft → issued → certified`
      with no void state, so a mistakenly-opened draft occupies its period permanently and FR-007
      returns it rather than letting anybody start again.
      [Gap, Spec §FR-007, Data-model §BillPackageStatus]
- [ ] CHK033 **Is deletion of a package specified at all?** Nothing in the spec or the contract
      refuses to delete an issued bill, and nothing permits deleting a draft. Silence here is how a
      period gets freed by removing the row that proved it was billed.
      [Gap, Spec §FR-044, Contract]

## 7 — The understatement that is reported and cannot be billed

The risk: FR-014b exists because freezing creates a leak. It reports the leak and stops there.

- [ ] CHK034 Is there a stated path to **bill** an understatement once reported? Feature 022
      attributes measurement by work date, so a report approved late whose work date falls in an
      already-billed period will never appear in any later period's proposal. FR-014b reports it;
      no requirement says how the quantity is recovered. [Gap, Spec §FR-014b, §FR-003]
- [ ] CHK035 If the remedy is an over-claim on the next bill (FR-006 permits one, with a reason),
      is that stated? A remedy that exists only as an implication will be found by one engineer and
      not the next, and the two bills will differ. [Traceability, Spec §FR-006, §FR-014b]
- [ ] CHK036 Is a tolerance stated for FR-014b's comparison? `Decimal(18,3)` arithmetic is exact, so
      the honest tolerance is zero — but the requirement does not say so, and an implementer who
      assumes a float tolerance will hide small understatements.
      [Gap, Spec §FR-014b]
- [ ] CHK037 Does FR-014b say **when** it is answered — on demand, on composition of the next bill,
      or on a schedule? A report nobody runs is the same as no report, which is the conclusion 022
      reached about its own reconciliation requirement. [Gap, Spec §FR-014b]
- [ ] CHK038 Does FR-048's reversal discrepancy share FR-014b's mechanism, as plan Phase F requires,
      or is it a second comparison? Two implementations of one comparison disagree, and the spec
      states the two requirements separately with no link.
      [Traceability, Spec §FR-014b, §FR-048, Plan §Phase F]
- [ ] CHK039 Is FR-006a's count given a denominator? Its stated purpose is that over-claiming "can
      be observed as a pattern"; three over-claims out of five lines and three out of 312 are the
      same count and different facts. [Measurability, Spec §FR-006a]

## 8 — 312 sheets in one workbook

The risk: a workbook with a missing sheet opens perfectly.

- [ ] CHK040 **Is a measurement sheet's name specified?** A spreadsheet sheet name is capped at 31
      characters, cannot contain `: \ / ? * [ ]`, and must be unique in the workbook. 312 sheets
      named from BOQ numbers or descriptions will collide or be truncated, and the library's
      response to a collision — throw, rename, or replace — decides whether an item silently
      vanishes. No requirement addresses naming at all.
      [Gap, Spec §FR-024, §FR-030]
- [ ] CHK041 Is FR-030 testable without knowing the item count? An assertion over the sheets a
      workbook contains passes just as happily over a short list; the plan requires a **count**
      assertion, but FR-030 does not say the count must equal the project's own and be assertable
      as such. 022 needed FR-037a for precisely this. [Measurability, Spec §FR-030]
- [ ] CHK042 Is "one measurement sheet per BOQ item" the same set as FR-003's proposed lines? For
      the subcontractor direction those are award lines (CHK008), and a sheet per BOQ item would be
      the wrong population. [Clarity, Spec §FR-003, §FR-030]
- [ ] CHK043 Is FR-029's "without truncation" bounded by anything the format can hold? A cell has a
      32,767-character limit and the real descriptions are multi-paragraph; nothing states what
      happens at the limit, and silent truncation is the default behaviour of every writer.
      [Gap, Spec §FR-029]
- [ ] CHK044 Are the plan's workbook limits — under 10 s and under 20 MB for 312 sheets — stated as
      requirements anywhere? They appear only in plan Technical Context, so no success criterion
      would fail if a package took four minutes. [Traceability, Plan §Performance Goals]

## 9 — The probe, and the half-proven policy

The risk: four new policies, a role that is exempt from all of them, and a suite that reports a
skip as a pass.

- [ ] CHK045 Does FR-050 require the non-vacuity assertion — that the restricted role was actually
      created — to run **first**? Both the plan and data-model.md say it must; FR-050 says only that
      the tables be "covered by a test exercising it". 022 made this FR-040a for the same reason.
      [Gap, Spec §FR-050]
- [ ] CHK046 Does FR-050 state that a skipped isolation test reports as **skipped and never as
      passed**? Existing suites in this repository warn and return, which a continuous-integration
      summary counts as a pass. [Gap, Spec §FR-050]
- [ ] CHK047 Does FR-050 require the `WITH CHECK` half to be exercised, not only the read? A probe
      that proves another company's rows are invisible says nothing about whether a row can be
      *written* into another company. [Gap, Spec §FR-050, Data-model §Row-level security]
- [ ] CHK048 Is `BillPackageLineClaim`'s isolation stated as its own, given it is reached through its
      package? It carries `companyId`, so the policy is direct — but research §7 records that the
      neighbouring `DWRTask` is protected by a parent lookup instead, and a policy copied from the
      wrong neighbour either hides every row or none.
      [Clarity, Data-model §Row-level security, Research §7]

## 10 — Reports nobody reads

- [ ] CHK049 Where are FR-027's missing identifiers reported? The workbook is a file download, and
      `missingHeaderFields` is a column on the row. Nothing states that a caller is told, so the
      most likely implementation records the gap and shows nobody.
      [Gap, Spec §FR-027, Data-model §BillPackage]
- [ ] CHK050 Does FR-043 state where the check-list gaps are reported, given it must not refuse the
      issue? "MUST report the gaps" with no addressee is satisfied by storing them.
      [Gap, Spec §FR-043]
- [ ] CHK051 Is a cumulative claim beyond an item's scope quantity specified? The real Annexure
      carries a Balance Qty that would go negative, and 018 flags over-scope rather than refusing
      it; 023 says nothing, so a negative balance may print as a positive.
      [Gap, Spec §FR-012, Schema §ClientBillLine.exceedsScope]
- [ ] CHK052 Does a reduction reason survive an edit that returns the claim to its proposal? FR-005
      stores "the reason where one was given" and FR-004 requires one only for a reduction, so a
      stale reason can sit beside a zero variance — arguing for a deduction the bill does not make.
      [Gap, Spec §FR-004, §FR-005]

## Findings

Nine items above are defects in the written requirements rather than questions for a reviewer. They
are left unchecked deliberately: the author marking their own findings satisfied is the same error
this checklist exists to catch.

| Item | Finding | Why it is a silent failure |
|---|---|---|
| **CHK002** | FR-035's footer identity is a rearrangement of data-model.md's definition of up-to-previous, so it holds for any values | The test the plan names as the package's one cross-bill property cannot fail |
| **CHK008** | FR-003 proposes "every BOQ line in the project" for both directions; a subcontractor bill measures award lines | 312 lines on a 17-line bill, or a quietly wrong population |
| **CHK010** | An award line mapping to no BOQ line has no measurement source, and zero is the obvious output | "Nothing was done" and "nothing could be read" are the same number on the direction billed monthly |
| **CHK016** | No requirement states what the release-withheld amount does to the taxable base, and it is zero on the only document the tests reproduce | Every non-zero withholding is untested arithmetic |
| **CHK021** | FR-020 is satisfied by an implementation that does nothing, because no figure records what a one-time deduction totals | A deduction re-recovered or never completed, with the requirement reading as met |
| **CHK025** | FR-039's live register and FR-028's frozen workbook contradict each other, and quickstart Pass 6 expects the live behaviour | A re-produced bill differs from the signed copy, or the register loses its running total |
| **CHK028** | FR-037's one-bill rule is stated sequentially; the concurrent case lives only in data-model.md as a design | A debit recovered twice is money taken twice |
| **CHK033** | Neither deletion nor abandonment of a package is addressed, and there is no void status | The only way out of a mistaken draft is deleting the row that proved a period was billed |
| **CHK040** | Sheet naming is unspecified against a 31-character cap, a reserved-character set and a uniqueness rule | A colliding or over-long name loses an item's sheet from a workbook that still opens |

### Also worth the reviewer's attention

CHK013 (SC-003 is not reproducible from the figures it states — 9,04,301 of recoveries are
missing), CHK014 (no rounding rule, against a document whose figures are whole rupees), CHK029
(FR-002's overlap scoped per project rather than per direction and counterparty) and CHK034 (the
understatement FR-014b reports has no stated route onto any later bill) are each a defect too, but
each has more than one defensible answer and the choice is the reviewer's rather than the author's.
